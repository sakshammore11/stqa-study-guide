Software testing is a rigorous engineering discipline of discovering defects early, measuring product quality, ensuring adherence to SRS, and safeguarding stakeholder confidence.

Topic 1.1

Software Testing Goals, Core Terminology & Severity/Priority

10-Mark Frequently Asked

7 Core Goals of Software Testing (From Notes Q.1A)

1
Detect Defects (Bugs): Find faults early, when correction is often cheaper and less disruptive than after release.
2
Verify Requirements: Check that the software’s behavior can be traced to functional and non-functional requirements in the SRS; testing helps reveal mismatches.
3
Ensure Correctness & Reliability: Evaluate outputs, error handling, and behavior under expected use and sustained load.
4
Validate User Needs: Confirm the software solves the actual business workflow comfortably and efficiently for end-users.
5
Improve Security & Integrity: Find weaknesses such as injection flaws or privilege escalation risks, and check whether data protections work as intended.
6
Reduce Risk & Cost: Finding a defect before release usually limits its impact and makes the change cheaper to contain.
7
Compliance with Standards: Follow applicable quality, safety, security, and accessibility standards and regulations.
MEMORY LINE · D V E V S R C

“Diligent Verifiers Ensure Valuable Software, Reduce Costs.”

  1. Detect defects
  2. Verify requirements
  3. Ensure correctness and reliability
  4. Validate user needs
  5. Secure data and system integrity
  6. Reduce risk and cost
  7. Comply with standards
Use the initials to recall the list; explain each goal in your own words in an exam answer.

Testing Terminology Chain (Notes Q.1)

1. Human Mistake
ERROR

A mistake, misconception, or action made by a developer during requirements, design, or coding.

e.g., developer accidentally writes "return a - b" instead of "a + b"
➔
2. In Source Code / Document
FAULT (BUG / DEFECT)

The static flaw or incorrect step in software that causes wrong execution.

e.g., "return a - b;" exists in compiled binary
➔
3. At Runtime Execution
FAILURE

An inability of the software to perform its required function within specified limits.

e.g., user inputs 5 + 3, system produces 2 or crashes!
Test Case: A formalized set of preconditions, input values, execution steps, expected outputs, and postconditions designed for a test objective.
Test Oracle: The authoritative ground-truth reference or benchmark (SRS, legacy system, manual calculator) used to evaluate whether actual == expected.
DEFECT CHAIN

Error in a person’s thinking → Fault in an artifact → Failure during execution.

Memory hook: mistake → code flaw → observed wrong behavior.
THE SEVEN TESTING PRINCIPLES · EXAM RECALL

“Early Testers Expect Defects; Pesticides Change Approach.”

  1. Early testing prevents late rework
  2. Testing shows defects are present, not absent
  3. Exhaustive testing is impossible
  4. Defects cluster in a small number of areas
  5. Pesticide paradox: refresh tests to find new bugs
  6. Context changes the right test approach
  7. Absence of known errors does not prove fitness
Use the sentence to recall the headings; add one sentence of explanation and an example for each in a long answer.

Severity vs Priority — Crucial University 5-Mark Question

Severity is the technical impact of a defect on system functionality (Critical, Major, Minor, Trivial). Priority is the business urgency of fixing the defect (High, Medium, Low).

FAST DISTINCTION

Severity = impact on the product. Priority = urgency in the queue.

Ask two separate questions: “How bad is the failure?” and “How soon must we fix it?”
High Severity + High Priority

1. Critical Blocker on Core Path

System crashes on user login or database transaction halts. Must be fixed immediately before testing continues.

High Severity + Low Priority

2. Severe Crash on Obsolete/Rare Config

System crashes when run on Windows 98 or printing to an obsolete dot-matrix printer. Technical impact is fatal, but business priority is low.

Low Severity + High Priority

3. Brand/Visual Blunder on Public Page

Company name misspelled on the homepage ("Microsft") or wrong logo on payment gateway. Functionality works fine, but severe brand damage requires immediate fix.

Low Severity + Low Priority

4. Minor Cosmetic Glitch

Slight pixel misalignment or faint font size difference in the privacy policy footnote. Fixed when time permits.

Testing models structure how verification (static reviews) and validation (dynamic test runs) align with the Software Development Life Cycle (SDLC).

User specifications, SRS, BRD documents.

Acceptance Testing (UAT)

System Testing

Validates individual code routines against Coding.

The W-Model (Dual V-Model)

An extension of the V-Model where testing activities begin on Day 1 parallel to development. For every development step (Requirements, HLD, LLD), there is a parallel testing verification process running simultaneously.

  • V1 (Development): User Requirements ➔ System Design ➔ Detailed Design ➔ Coding.
  • V2 (Testing): Review Requirements ➔ Review System Design ➔ Review Detailed Design ➔ Execute Code Tests.

Core Advantage: Eliminates defect slippage by treating static reviews as equal partners to dynamic testing.

Topic 1.2

Verification — Requirements, High Level Design, Low Level Design & Code

Static Testing Pillar
VERIFICATION ≠ VALIDATION

Verification: “Are we building the product right?” Review the work products against their specifications. Validation: “Are we building the right product?” Exercise the software against user needs.

Verification is the static evaluation process of checking whether the intermediate products of a development phase satisfy the conditions imposed at the start of that phase ("Are we building the product right?").

📄

1. Verification of Requirements

Static examination of SRS & BRD documents for completeness, consistency, feasibility, and testability. Eliminates ambiguities like "system must respond quickly".

Ambiguity checks RTM coverage Testability
🏛️

2. Verification of High Level Design (HLD)

Checks overall architecture, modularity, data flow, subsystem decomposition, database schemas, and external API interfaces (Notes Q.1B).

Architecture Modularity Traceability Feasibility
⚙️

3. Verification of Low Level Design (LLD)

Inspects detailed internal class designs, method signatures, data structures, state charts, algorithmic complexity, and error-handling routines before coding.

Class logic Algorithms Exception handling
💻

4. Verification of Code

Peer code reviews, desk checking, structured walkthroughs, Fagan inspections, and automated static analyzers (SonarQube, ESLint) to catch syntax and logic flaws.

Standards Memory safety Static analysis
Topic 1.3

Validation — Unit, Integration, Function, Sanity, System & Acceptance

Dynamic Execution Pillar
INTEGRATION TESTING · REMEMBER THE TEST DOUBLE

“Top-down uses Stubs; Bottom-up uses Drivers.” A stub stands in for a lower module that has not been integrated yet. A driver calls a lower-level module when the higher-level caller is not ready.

Validation is the dynamic evaluation process of executing the actual compiled software on target test environments to check whether it satisfies user needs and business goals ("Are we building the right product?").

Integration Strategies: Stubs vs Drivers (Crucial Exam Concept)

When testing modules in incremental integration, missing subordinate or superordinate modules must be replaced with dummy code.

Top-Down Integration (Uses STUBS)

Starts from the top-level calling module down to sub-modules. If lower modules are not yet developed, dummy STUBS are used to simulate responses.

STUB Definition: A dummy called routine that receives calls from a higher-level module and returns hardcoded simulated responses.
Bottom-Up Integration (Uses DRIVERS)

Starts from lowest-level atomic modules up to higher callers. If the parent module is not ready, a dummy DRIVER is written to invoke the test unit.

DRIVER Definition: A dummy calling routine that invokes the lower module under test, passes test data, and collects the returned output.

Unit Testing

Tests individual functions or procedures in complete isolation. Performed by developers using frameworks like pytest, JUnit.

assert add(2, 3) == 5

Integration Testing

Tests interface communication between connected modules. Includes Pair-wise (Notes Q.1C), Big-Bang, Top-Down, Bottom-Up, and Sandwich approaches. Here, pair-wise means testing module pairs; it is different from combinatorial all-pairs testing of input values.

Function Testing

Verifies software features against functional requirement specifications without regard to internal system architecture.

Sanity Testing

A quick, focused subset of regression testing performed on a stable build to verify that a specific bug fix actually works without breaking major features.

System Testing

End-to-end testing of the complete software system against SRS: Performance, Load, Stress, Security, Disaster Recovery, and Compatibility.

Acceptance Testing (UAT)

Final sign-off by end-users. Includes Alpha Testing (internal site, controlled) and Beta Testing (real customer environment).

Topic 2.1

Static Testing — Reviews, Structured Walkthrough & Fagan Inspection

10M Theory Exam Core

1. Reviews

Manual verification of work products by one or more peers:

  • Informal Review: Casual peer desk-check; no pre-meeting notes or defect metrics logged.
  • Formal Review: Pre-scheduled with strict agenda, entry/exit criteria, and documented minutes.
  • Technical Review: Conducted by technical architects and peers to verify engineering decisions.

2. Structured Walkthrough (Notes Q.2A)

An informal to semi-formal review led by the Author:

Moderator (Chairs meeting) Author (Presents code) Reviewers (Find bugs) Scribe (Takes notes)
6 Sequential Steps:

1. Planning ➔ 2. Overview ➔ 3. Individual Review ➔ 4. Walkthrough Meeting ➔ 5. Rework ➔ 6. Follow-up.

3. Fagan Inspection

The most formal, rigorous static defect detection method:

  • Led by a trained, independent Moderator (never the author!).
  • Strict 6-step lifecycle: Planning, Overview, Preparation, Inspection Meeting, Rework, Follow-up.
  • Defect metrics, inspection checklists, and defect densities are formally recorded for CMMI quality audit.
WALKTHROUGH · SIX STEPS
1 Plan2 Overview3 Individual review4 Meeting5 Rework6 Follow-up
Recall the sequence as P-O-R-M-R-F. Do not mix it with Fagan inspection’s Preparation step.

Static Analysis Tools (Notes Page 12)

Automated software tools that parse source code without running it to detect syntax errors, dead code, memory leaks, security vulnerabilities, and coding standard violations.

SonarQube: Continuous code quality, technical debt, security hotspots.
ESLint: JavaScript/TypeScript linting, style & syntax rules.
Checkstyle: Java adherence to corporate coding standards.
PMD / FindBugs: Unused variables, empty catch blocks, dead objects.
Topic 2.2 (White Box)

Basis Path Testing, Control Flow Graph (CFG) & Cyclomatic Complexity

High-value practice question

White-box (structural) testing examines internal code structure. Basis Path Testing uses cyclomatic complexity to choose a set of linearly independent execution paths. A feasible basis suite provides strong statement and branch coverage for the represented control-flow graph.

3 Equivalent Methods for Cyclomatic Complexity V(G)

Method 1 (Predicate Nodes)
V(G) = P + 1
P = Number of predicate decision nodes (if, while, for)
Method 2 (Edges & Nodes)
V(G) = E - N + 2
E = Flow edges, N = CFG execution nodes
Method 3 (Regions)
V(G) = R
R = Enclosed planar regions + 1 unbounded outer region
CYCLOMATIC COMPLEXITY · THREE WAYS TO CHECK

“Decisions + 1 · Edges − Nodes + 2 · Regions.”

Example: 1 decision, 6 edges, 6 nodes, 2 regionsP + 1 = 1 + 1 = 2E − N + 2 = 6 − 6 + 2 = 2R = 2
All three should agree for a connected control-flow graph. V(G) gives the number of linearly independent paths, not every possible execution path.

Loop Testing

Focuses on validity of loop boundary iterations:

  • Simple Loops ($n$ max passes): Test 0 passes, 1 pass, 2 passes, typical $m$ passes, $n-1$, $n$, and $n+1$ passes.
  • Nested Loops: Start at innermost loop, hold outer loops at minimum values, and work outwards.
  • Concatenated Loops: If loops are independent, test each separately; if dependent, treat as nested.

Data Flow Testing

Selects test paths according to the lifecycle of variables:

  • Definition ($d$): Variable is created or assigned value.
  • Usage ($u$): Predicate use ($p$-use in if-conditions) or Computation use ($c$-use in expressions).
  • du-path: Definition-clear path from variable definition to usage.

Mutation Testing

Evaluates the quality of a test suite by injecting synthetic bugs (mutants):

  • Mutant: Code version with a deliberate fault (e.g. changing > to >=).
  • Killed: Test case fails, exposing the fault.
  • Survived: All tests pass, exposing a test hole.
  • Score: $MS = [K / (M - E)] \times 100\%$.
Topic 2.2 (Black Box)

Boundary Value Analysis (BVA), Equivalence Class Testing (ECT) & Decision Tables

Essential University Numericals

Boundary Value Analysis (BVA) Formulas for $n$ Variables

Recall: Standard BVC = 4 boundary points per input + one all-nominal case; Robust adds two invalid points per input; Worst-case takes the Cartesian product of the five valid values for every input.

Technique Values Evaluated per Variable Formula ($n$ variables) Example (3 Variables)
Standard BVC $min, min+1, nom, max-1, max$ (Valid only) 4n + 1 $4(3) + 1 = \mathbf{13}$
Robust Testing $min-1, min, min+1, nom, max-1, max, max+1$ (Includes invalid) 6n + 1 $6(3) + 1 = \mathbf{19}$
Worst-Case Testing All combinations of $\{min, min+1, nom, max-1, max\}$ 5^n $5^3 = \mathbf{125}$
Robust Worst-Case All combinations of $\{min-1, min, min+1, nom, max-1, max, max+1\}$ 7^n $7^3 = \mathbf{343}$
BVA · COUNTS AT A GLANCE

4n + 1 standard · 6n + 1 robust · 5n worst-case.

Single-variable boundary checks grow linearly. Worst-case combinations multiply across inputs.
TEST LEVELS · U I S A

“Use It, Scale, Accept.”

Unit → Integration → System → Acceptance. Use the order to place a test in the hierarchy.
ACCESSIBILITY · POUR

Perceivable · Operable · Understandable · Robust

For each interface, ask: Can users perceive it, operate it, understand it, and use it with different technologies?

Equivalence Class Testing (ECT) Taxonomy

Partitions input domain into classes where every element within a class produces identical program behavior.

1
Weak Normal ECT: One test case from each valid equivalence class.
2
Strong Normal ECT: Cartesian product of valid classes from all inputs.
3
Weak Robust ECT: Tests one value from each invalid class alongside valid values for other variables.
4
Strong Robust ECT: Tests all combinations of both valid and invalid classes.

Decision Table Based Testing

Ideal for complex business logic with multiple Boolean conditions. Consists of 4 quadrants:

1. Condition Stub: List of input conditions / rules.
2. Condition Entry: Boolean values (T/F or Y/N).
3. Action Stub: List of possible outputs / actions.
4. Action Entry: Checkmarks (X) for fired actions.
For $C$ independent binary conditions, the full table has up to $2^C$ rules. Mark infeasible combinations as don’t-cares or simplify them only when the requirements justify it.

Usability & Accessibility Testing (Notes Q.3 Option 2)

Usability Testing

Tests how intuitive, easy, and pleasant the software is for human users. Focuses on Jakob Nielsen's 5 Quality Components:

  • Learnability: How easily first-time users accomplish basic tasks.
  • Efficiency: How quickly experienced users complete workflows.
  • Memorability: How easily users re-establish proficiency after a hiatus.
  • Errors: How many errors users make and how easily they recover.
  • Satisfaction: How pleasant the user interface feels.
Accessibility Testing (WCAG 2.2)

Ensures software is accessible to users with visual, auditory, motor, or cognitive disabilities. Built on the 4 POUR principles:

If your exam specifically asks for WCAG 2.1, use that syllabus wording. For current practice, W3C recommends using the latest version, WCAG 2.2; it adds criteria while keeping existing 2.1 criteria unchanged.

  • Perceivable: Content presented through multiple senses (alt text, captions).
  • Operable: UI operated via keyboard alone; no time-limited traps.
  • Understandable: Clear text, predictable navigation, error guidance.
  • Robust: Compatible with assistive technologies (screen readers like NVDA, VoiceOver).
Topic 2.3

Regression Testing — Objectives, Need & Types

10M Theory Exam Core (Notes Q.2B)

What & Why Regression Testing?

Definition: Re-running previously passed test cases to ensure that recent code modifications, bug fixes, or enhancements have not unintentionally broken existing functionalities.

Trigger Events (When is it performed?):
  • After fixing a reported bug or defect.
  • After adding a new feature or module to the codebase.
  • After software refactoring or performance optimization.
  • After underlying OS, database, or dependency updates.

Types of Regression Testing

1
Retest-All: Re-executes the entire suite of test cases. Very safe but computationally expensive.
2
Selective Regression: Only runs test cases affected by the modified modules or dependent components.
3
Progressive Regression: Applied when specifications change, designing new test cases without breaking old ones.
4
Corrective Regression: Done when no changes were made to specifications, re-using existing test cases.
REGRESSION · FOUR COMMON TYPES

“Careful Planners Retest Selectively” → Corrective · Progressive · Retest-all · Selective.

Corrective reuses existing tests when requirements are unchanged; progressive adds or adapts tests for changed requirements.
